# MVP 範圍

這次要做什麼、不做什麼、為什麼。

---

## 這是一個驗證實驗，不是產品原型

我們不做完整 prototype。目標是用最小、快、有 AI 協助的方式，回答兩個問題：

1. AI 追問的**進階問題**，命不命中面試官真正會問的
2. AI 給的**行動推薦**，有沒有人真的照做並派上用場

這兩個是我們認為的主要價值所在，所以驗證就對著它們做。做出一個漂亮的產品原型要三週，做完仍然不知道歸納準不準；這條路便宜、快，而且會產出一個能推翻假設的答案。

## 為什麼是這兩個功能

它們對應到兩個核心利基點：

- **進階問題** → N16 經歷歸納協助度。AI 讀完你的經歷後，能不能問出你自己沒交代清楚的地方，就是「幫你歸納」這一步有沒有價值的直接證據。
- **行動推薦** → N19 可驗證性。AI 給的建議有沒有被採用、有沒有用，是「給完建議就結束」這個市場通病能不能被解掉的直接證據。

如果 AI 問出來的都是罐頭問題、給的建議沒人照做，那 N16 / N19 就是假的利基點，越早知道越好。

## 必做

每個人的分支都要能跑完這個最小流程：

| | 內容 |
|---|---|
| 輸入 | 一份候選人背景（經歷／履歷）＋ 一份 JD |
| 處理 | 你設計的 prompt |
| 輸出一 | 進階問題：AI 認為此人最可能被追問的 N 個問題 |
| 輸出二 | 行動推薦：AI 給的面試前準備建議 |
| 紀錄 | 輸出結果要能存下來，之後跟標準答案對照 |

形式不限——Python 腳本、Colab、n8n、Dify、一個網頁、甚至只有一份 prompt 加 Google Sheet 都可以。跑得動、留得下紀錄就算數。

## 選做

行有餘力再說，不影響驗證：

- 適配度判斷（AI 評估此人與 JD 的契合程度）——可以順手輸出並記錄，但它是**觀察值，不是驗證指標**
- 結果的視覺化呈現
- 多個 JD 的批次處理

## 不做

- **前端介面**。目前沒有任何驗證問題需要靠介面才能回答。
- **登入、帳號、資料庫**。
- **Dashboard 與第一階段的基本資料填寫流程**。這正是我們擔心使用者走不到的地方，所以這次直接跳過，先驗證後半段的結果有沒有價值。
- **#3 每週一題、#4 目標獎勵、#5 mentor 媒合、#6 同儕小組**。這些在 Roadmap 上是 Now 之後的事，不在這次範圍。

## 三個人各做什麼

三支分支做的是**同一個命題的不同解法**：自己版本的 prompt 設計與結果呈現方式，跑同一批語料，比誰問得更準。

| 人 | 分支 | 語料分工 |
|---|---|---|
| Alan | `mvp/alan` | 面試心得 10 筆 |
| Berry | `mvp/berry` | 面試心得 10 筆 |
| Sunny | `mvp/sunny` | 面試心得 10 筆 |

蒐集到的語料統一整理進 `assets/fixtures/`，透過 PR 進 `main`，讓三支分支測的是同一批輸入。**輸入相同，比較才有意義。**

語料的蒐集方式與格式見 [`validation-plan.md`](validation-plan.md)。

## 收斂怎麼比

- **進階問題**：命中率。三個人的 prompt 跑同一批 30 筆語料，看誰預測的問題命中面試官實際問題最多。這是可以直接排序的數字。
- **行動推薦**：質性。聽三個人講「哪幾條建議在真實面試裡真的被照做了」。樣本少，但模式聽得出來。
- **取捨說明**：每人講一次自己版本做了什麼取捨、為什麼。這部分沒有分數，但通常是最有價值的討論。

判準的細節與限制見 [`validation-plan.md`](validation-plan.md)。

## 這次不驗證的事

講清楚以免收斂時吵錯方向：

- **Persona 準不準**。Persona 只能被真人推翻，這次的語料是公開心得，測不到。
- **使用者願不願意付錢**。
- **長期留存**。護城河是累積，但累積需要時間，這次的時間尺度測不到。
- **AI 的適配度判斷準不準**。訊號太雜，見 [`validation-plan.md`](validation-plan.md) 的說明。

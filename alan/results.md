# 跑分結果 — A/B/C 三組對照

**問的問題**：AI 預測面試問題的命中率，有多少來自「讀了候選人的經歷」，有多少只是「面試題本來就可預測」？

Berry 的實驗有 B 和 C（77% / 88%）但沒有 A，所以無法回答這個問題。本次補上基準線。

日期：2026-08-18　語料：7 筆（沿用 `mvp/berry` 整理，原文已核對，見 [source-audit.md](source-audit.md)）
執行：`./run.sh <組名>`，`claude -p`，盲測由腳本切掉答案段保證。命中判定為 Alan + Claude，**收斂日三人重判**。

---

## 三組是什麼

| 組 | 給 AI 的輸入 | 測的是 |
|---|---|---|
| **A** baseline | 只有產業 + 職位 | 面試題本身的可預測性 |
| **B** with background | 產業 + 職位 + 候選人背景 | **B − A = 讀經歷的增益（N16 的證據）** |
| **C** adaptive | 同 B，但 prompt 先判職位型態再分配題型名額 | **C − B = prompt 設計的增益** |

三組都固定猜 8 題。A 與 B 的 prompt 只差「有沒有背景」一句，其餘逐字相同。

## 四個發現

### 1. 「給 AI 看經歷」本身幾乎沒有用（B − A = +2.6pt）

這是今天最重要、也最不利於我們原本假設的數字。

N16 主張「AI 讀完你的經歷能問得更準」。但在 5 筆硬語料上，加了背景之後嚴格命中率只從 25.9% 走到 28.5%，
其中 tech-pm-01 還**掉了**（37.5% → 25.0%）——因為 B 組讀完背景後全力追問轉職邏輯與經歷細節，
反而漏掉了「自我介紹」這種一定會問的題，而 A 組因為沒東西可挖，開場就猜了自我介紹。

**光是「餵經歷給 AI」不構成護城河。** 這一步 ChatGPT 也做得到，而且做完沒有比不做好多少。

### 2. 有用的是「怎麼問」，不是「有沒有經歷」（C − B = +9.1pt）

C 組贏在 prompt 逼它做兩件事：先判職位型態決定題型配額，以及要求問題往下鑽一層。
增益是 B − A 的三倍多。價值不在資料，在對資料的處理方式。

### 3. 經歷追問題上，差距是量級的（A 30% → C 90%）

★ 題是「非讀懂這個人的背景就問不出來」的題目（KPI 制定標準、PIP 流程、Repository 設計選擇）。
在這 5 題上 C 組拿到 90%，A 組 30%。**N16 是真的，但它的射程很窄。**

窄在哪裡：硬語料 34 題裡只有 5 題是 ★ 題，約 15%。
換句話說，這個能力在真實面試裡只覆蓋到七分之一的題目——很強，但不是全部。

### 4. C 組在 backend-01 上輸給 A 與 B（66.7% → 33.3%）

C 組把「知識密集型」的名額配給了很細的技術題（PHP-FPM 的 `pm.max_children` 怎麼算、
MySQL 複合索引最左前綴），而面試官實際問的是高併發怎麼處理這種主軸題。
**細節深度不等於命中率。** Berry 的 v2 在 frontend 掉分（78% → 67%）撞的是同一面牆：
往下鑽會鑽偏。這是 C 組下一版要修的地方。

## 語料分級的效果

軟語料的命中率系統性偏高：A 組在硬語料只有 25.9%，在軟語料有 40%。
因為「說明代表性專案」這種答案任何 prompt 都會命中。**如果不分級，基準線會被墊高，三組的差距會被壓縮。**
這也意味著 Berry 的 77% → 88% 有一部分來自那兩筆軟語料。

## 判定爭議（留給收斂日三人裁決）

1. tech-pm-01 實際問「業務部門 KPI 的制定標準」，C 組問「單店 KPI 的目標值是誰訂的、依據什麼算出來的」——算 ✅ 還是 🔶？（我判 ✅）
2. tech-pm-01 實際問「PIP 執行流程和成效」，C 組問「客服團隊原本的績效問題是什麼、你做了什麼、哪個數字有變」——算命中嗎？（我判 ✅；Berry 在他的 SOP 裡也記了同一個爭議）
3. 實際問「用英文介紹最近看過的電影」，C 組問「用英文介紹你管過的一個專案」——題型對了、內容錯了。（我判 🔶）
4. 實際問「為什麼想進入科技產業」，A 組問「為什麼想加入我們公司」——動機題算同一題嗎？（我判 ✅）
5. software-engineer-01 實際問「virtual 與 static 的作用」，C 組問「virtual function 怎麼實作、vtable 配置」——（我判 ✅，但只涵蓋一半）
6. 一個 AI 問題同時對應到答案裡兩題（例：Redux 與 Hooks／前端資料流），該算兩次命中還是一次？（我算兩次，這會讓命中率偏高）

## 已知偏誤

- **固定猜 8 題，實際題數 3 到 9 不等。** backend-01 只有 3 題，猜 8 題等於亂槍打鳥（所以三組在那筆都偏高）；frontend-01 有 9 題，天花板 89%。三組受影響相同，不影響組間比較，但單筆絕對值不可信。
- **7 筆來自 5 位作者**，有效獨立樣本約 5。
- **命中判定是我一個人判的**，判準尚未與 Berry、Sunny 對齊。
- **語料量遠低於 `validation-plan.md` 的 30 筆目標**，本次結論只能看量級差距，不能看百分點差距。

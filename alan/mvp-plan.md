分支：`mvp/alan`　撰寫日：2026-08-22
狀態：計畫階段，尚未開發

## 為什麼有這份計畫

第一輪實驗（A/B/C 三組盲測，7 筆語料，見 [results.md](results.md)）測完了 N16 的一半，
結論是「讀經歷本身增益有限，真正有用的是問法設計」。N19 到目前為止一筆資料都沒有。

`docs/mvp-scope.md` 對 N19 的驗證方法寫的是「用真實面試做質性訪談」。
Alan 本人在 2026-08-24 至 09-05 之間有一場真實面試，這是這輪唯一的真實面試機會，
所以這份計畫圍繞那場面試安排。

這份計畫的定位是**個人分支上的加碼**，不改變三人共同交付物。
共同交付物仍然是 A/B/C 三組對照的實驗結果與命中率比較。

## 一、要驗證什麼指標

### 主指標：N19 可驗證性 — 行動推薦的採用與效用

AI 給的面試準備建議，有沒有被真的照做，照做之後有沒有派上用場。

這是 `docs/mvp-scope.md` 列的兩個必驗項目中，唯一還沒碰的那個。

### 次指標：N16 經歷歸納協助度 — 在真實面試上的閉環驗證

AI 依經歷追問出的進階問題，命不命中面試官真正問的。

第一輪已用 7 筆公開心得盲測過，這輪不是為了增加樣本（n=1 不改變統計），
而是為了取得一筆**從輸入到面試結果的完整閉環資料**。這是七筆公開心得做不到的事：
公開心得是別人寫完的結果，這一筆是自己走過的過程。

兩個指標的硬門檻都要靠面試發生後的真實結果才能判定，這點不會變——
但 N19（履歷類建議）跟 N16（缺口診斷）各自有一段今天就能先跑的快速代理
迴圈，不用整段乾等面試，詳見〈環節與指標的對應〉。

### 什麼結果算失敗（面試前定好）

n=1 沒有統計意義，所以這些不是顯著性門檻，是**預先寫死的解讀規則**——
避免事後把任何結果都講成成功。門檻在面試前定，面試後不改。

| 指標 | 不成立 | 存疑 | 有證據 |
|---|---|---|---|
| **N19 行動推薦** | 「做了且用上」0 條 | 1 條 | 2 條以上 |
| **N16 進階問題** | 命中率低於 20% | 20%–35% | 35% 以上 |
| **N16 缺口診斷** | AI 指出的落差，面試中一個都沒成為問題 | 有被碰到但沒被追問 | 至少 1 個成為實際被追問或答不好的點 |

N16 進階問題的門檻用**命中題數 ÷ 面試官實際題數**計算，
對照組是第一輪盲測 C 組的嚴格命中率 37.6%。低於 20% 表示真實情境下的表現
明顯差於盲測，那代表盲測的結果無法外推到真實面試。

行動推薦以產出 5 條為前提。若實際產出條數不同，門檻按比例調整
（不成立 = 0 條，有證據 = 四成以上）。

### 什麼情況這場面試不算數

- **面試官問的問題少於 4 題。** 第一輪的 backend-01 只有 3 題，
  固定猜 8 題等於亂槍打鳥，命中率會虛高。題數太少時 N16 的結論作廢，
  N19 不受影響（建議有沒有用跟題數無關）。
- **面試被取消或延到收斂日之後。** N16／N19 的硬門檻都沒有資料，計畫改為
  「管線已備妥，等結果」；但缺口診斷與行動推薦——履歷類這兩項的快速代理
  資料（匹配分數變化，見〈環節與指標的對應〉）不受影響，今天就能先跑，
  收斂日至少不是完全空手。

### 這輪不驗證

沿用 `docs/mvp-scope.md` 的排除清單，另加兩項因受測者身分而失效的：

| 不驗證的項目 | 原因 |
|---|---|
| Persona 準不準 | 沿用共同決定，n=1 推翻不了 |
| 願不願意付錢 | 沿用共同決定 |
| 長期留存 | 沿用共同決定，時間尺度不足 |
| 適配度判斷準不準 | 沿用共同決定，訊號太雜 |
| 使用者願不願意完成填答 | 受測者是設計者本人，一定會填完，測不到漏斗 |
| 介面易用性 | 同上 |

### 已知偏誤（收斂日要主動講）

**受測者、設計者、判定者是同一人。** 這對兩個指標的影響不同：

- **N19 受影響嚴重。** 「這條建議我做了嗎」「有沒有派上用場」由 Alan 自己判，
  而 Alan 知道實驗要證明什麼，有動機讓它成立。這輪 N19 的產出應該被稱為**自我觀察**，
  不是驗證。它的用途是逼出一個下一輪可測的假設。履歷類建議的快速代理指標
  （匹配分數變化）不受這個偏誤影響——分數是重新跑 prompt 算出來的，不是
  Alan 自己判的——但它仍然只是代理指標，不是「用上了」的證據，兩件事不能
  混為一談（見〈環節與指標的對應〉2026-08-25 二次補記）。
- **N16 受影響輕微。** 面試官實際問了什麼不受 Alan 控制，事前也不知道，
  是外部的、無法造假的標準答案。這一半是硬的。

## 二、指標用什麼事件檢測

### N19 的四層判準

每一條行動推薦，走完下面四格。四格都是事實或事後對照，不是評分。

| 層 | 事件 | 記錄時機 |
|---|---|---|
| **採用意願** | 使用者在看到建議當下勾選「我打算做」 | 面試前 |
| **實際採用** | 面試前這條建議真的做了 | 面試後回填 |
| **派上用場** | 做了的那條，在面試現場真的用到了 | 面試後回填 |
| **主觀有用** | 這條建議有沒有幫助，1–5 評分（附記，不當主判準） | 面試後回填 |

「做了 / 用上了」兩格交叉出四種組合，各自有不同意義：

| | 用上了 | 沒用上 |
|---|---|---|
| **做了** | N19 成立的證據 | 建議方向錯了 |
| **沒做** | — | 追問「為什麼沒做」，這格的回答最有價值 |

**不用「面試上了沒」當判準。** 沿用 `CLAUDE.md` 的共同決定：那是一個 bit 的雜訊，
被薪資、內定、面試官偏好污染。

共同決定（2026-08-23 三人會議收斂版）把「求職信心」暫不列為主要驗證項目，行動推薦
（N19）的驗證方法收在兩塊：**主觀感受**（上面「主觀有用」1–5 評分）跟**數據**——
履歷依建議調整後重跑匹配分析，分數是否上升；再次投遞後面試邀請數量是否提升。

**匹配分數變化、面試邀請數量、面試上了沒，一律只當觀察附註，不進 N19 判定門檻**
（2026-08-25 補記）。理由跟排除「適配度判斷」是同一條邏輯：匹配分數是 AI
自己算的，用同一顆 AI 的分數去驗證同一顆 AI 給的建議有沒有用，單獨拿來當判準是
循環論證；面試邀請數量跟「面試上了沒」一樣，被履歷以外太多因素污染（市場時機、
公司當下缺額、篩履歷鬆緊）。N19 唯一的判定證據仍是上面「做了 × 用上了」
的回填比對。app.js 現有的「職缺匹配度分析」「投遞紀錄」功能維持現狀，不特地為此
擴充或降級。

### 環節與指標的對應（2026-08-25 補記）

行動推薦（`prompts/g-action-plan.md`）產出的建議，依內容分屬不同階段。
**這裡的原則統一：匹配分數變化不管用在哪個環節，都只是快速代理指標，
不滿足第 43-47 行的硬門檻**（2026-08-25 二次補記，修正前一版把履歷類
行動推薦當成確定性證據的錯誤——循環論證的疑慮跟建議屬於哪個階段無關，
是測量工具本身的問題，不能因為它是履歷類就破例）。硬門檻仍然只認
「做了 × 用上了」的真實回填比對，那格永遠要等面試發生。快速代理的
價值是「今天先有資料、先知道方向對不對」，不是提前拿到判定結果。

| 環節 | 對應指標 | 這輪的硬門檻能不能滿足 | 今天能不能先有代理資料 | 代理資料怎麼取得 |
|---|---|---|---|---|
| ②追問（認識自己） | 不屬於 N16／N19 | 不適用 | 不測 | 願不願意填答／填答深度要換真實受試者才測得出漏斗，Alan 自測一定會填完，留到第二輪 |
| 缺口診斷 | N16 另一半 | 不能，要等 Wave 2 | 能（快速代理） | 針對缺口採取行動、重跑匹配分析看落差有沒有位移 |
| 行動推薦——履歷類 | N19 | 不能，要等 Wave 2 | 能（快速代理） | 履歷依建議調整、重跑匹配分析看落差有沒有位移；這不是「用上了」的證據，是「方向有沒有對」的先行訊號 |
| 行動推薦——面試類 | N19 | 不能，要等 Wave 2 | 不能 | 做了／用上了回填比對，Wave 2 |
| 面試官提問預測（原「進階問題」，改名見〈待解問題〉） | N16 主指標 | 不能，要等 Wave 2 | 不能，無代理指標 | 命中率對照面試官實際問題，Wave 2；本質是猜一個不受控、事前不知道答案的外部事件，沒有捷徑 |

這輪五個環節的硬門檻全部卡在面試有沒有發生——這是這份計畫從頭到尾的
前提（面試是唯一不能談判的節點），沒有任何環節能繞過。差別只在於：
缺口診斷與行動推薦——履歷類這兩格，就算面試還沒發生，今天也能先跑出
一份代理資料，讓「管線已備妥，等結果」不是完全空手等，而是已經有
方向性的觀察可以先寫進去。

### N16 的兩個事件

| 事件 | 檢測方式 |
|---|---|
| **面試官提問預測命中**（原稱「進階問題命中」） | 面試後逐題回填「面試官實際問了什麼」，與 AI 事前產出的 8 題比對 |
| **缺口診斷命中** | AI 事前指出「你的資訊還缺 X」「你跟這份 JD 的落差在 Y」，面試後檢查 X / Y 是不是真的成為答不出來的地方；今天可先用匹配分數變化當快速代理指標 |

第二個事件是這輪新增的，第一輪沒有。它把 N16 從「問題猜得準不準」
延伸到「診斷準不準」，而診斷正是行動推薦的來源，所以它同時是 N19 的上游。

### 回填程序（降低自我判定偏誤）

受測者是設計者本人，最大的風險不是說謊，是**事後合理化**——
先看過 AI 的預測再回想面試內容，記憶會往猜中的方向靠。
以下程序在面試前就定好，成本接近零：

| 時點 | 動作 | 為什麼 |
|---|---|---|
| **面試前** | 看到行動推薦時勾選「我打算做」，存檔 | 承諾要在知道結果之前發生 |
| **面試前一天** | 記錄每條建議「做了 / 沒做」，存檔 | 「做了沒」是面試前的事實，不該事後回想 |
| **面試後、打開 AI 輸出之前** | 憑記憶寫下面試官實際問的每一題，存檔並記下時間 | 這是整個程序的關鍵。標準答案必須在看到預測之前產生 |
| **上一步存檔之後** | 才打開 AI 的 8 題做比對 | |
| **比對之後** | 填「用上了嗎」「沒做的原因」 | |

存檔指的是寫進檔案並 commit，時間戳由 git 紀錄。
這一條是收斂日被問「你自己判會不會偏」時唯一有力的答案。

### 事件對應到畫面

| 事件 | 發生在哪一頁 |
|---|---|
| 缺口診斷產生 | ② AI 追問頁 |
| 採用意願（勾選） | ④ 輸出頁 |
| 實際採用、派上用場、主觀有用 | ⑤ 回訪頁 |
| 進階問題命中 | ⑤ 回訪頁（回填後自動比對） |
| 缺口診斷命中 | ⑤ 回訪頁 + 事後訪談 |

## 四、User Story

五個畫面，一條時間線。每個畫面對應一段真實發生過的事。

### ① 輸入基本資訊

> 作為一個要準備面試的人，我想填入我的基本背景與這份 JD，
> 讓系統有足夠的材料開始理解我。

- 基本資訊採選填與填答混合（產業、年資、職位、目標職缺）
- 履歷與 JD 為非必填欄位（實際測試時會填）
- 完成後進入下一步

### ② AI 指出缺口並追問

> 作為一個講不清楚自己經歷的人，我想知道我的資訊哪裡不夠、
> 跟這份 JD 差在哪，並回答那些我自己沒想到要交代的問題。

- AI 輸出：資訊完整度判斷、與 JD 的落差、3~5 個追問
- 使用者補充回答
- **這一步是 N16 的入口，也是這輪新增的核心機制**

### ③ 個人輪廓

> 作為一個看不出自己經歷有什麼線索的人，
> 我想看到 AI 把我的經歷整理成一個可以理解的輪廓。

- 核心能力、經歷主線、可能的短板、與 JD 的落差
- 這一頁是行動推薦的來源，不是裝飾

### ④ 進階問題與行動推薦

> 作為一個要去面試的人，我想知道面試官可能會問我什麼、
> 以及我現在該做哪幾件事。

- 進階問題 8 題（沿用 C 組 prompt，待改名為「面試官提問預測」，見〈待解問題〉）
- 行動推薦 3~5 條，每條可勾選「我打算做」，並標記屬於履歷類或面試類
  （見〈環節與指標的對應〉）——這個標記決定回訪頁要走哪一種驗證欄位
- 勾選這個動作把建議變成承諾，是 N19 第一層的事件
- 履歷類建議額外多一步：做完後可以重跑匹配分析，記錄分數變化——這是
  今天就能跑的快速代理，不等於「用上了」，見下方 Wave 1

### ⑤ 面試後回訪

> 作為一個面試完的人，我想回來記錄實際發生了什麼，
> 看看當初那些建議與預測到底準不準。

- 逐題回填面試官實際問了什麼，系統標出哪幾題猜中
- 每條建議填：做了嗎 / 用上了嗎 / 沒做的原因
- **這一頁是整個 demo 唯一不可省的部分。** 18 個競品的可驗證性分數全部偏低，
  空的就是這一格：給完建議就結束，沒有人回來問準不準。

### 累積視角（這輪不做畫面）

> 作為一個投了很多家的人，我想看到我投遞的軌跡與累積的模式。

⑤ 回訪頁存下來的資料就是累積的第一塊磚，但檢視畫面這輪不做——
它要有意義需要同一個人面試很多次，這輪只有一筆，做出來會是空面板。
若收斂日前有餘裕，可以用示意資料做一個靜態畫面說明產品全貌。

## 排程

面試日期是唯一不能談判的節點。收斂日目前未知，以下按最壞情況（面試 8/26）排。

### Wave 1 — 面試前必須完成

1. 兩個新 prompt（缺口診斷、行動推薦）寫好並試跑（已完成，見 `alan/prompts/d-gap-diagnosis.md`、`g-action-plan.md`）
2. Alan 填自己的基本資訊、履歷、目標 JD
3. 跑完 ②③④，把進階問題與行動推薦定稿，行動推薦逐條標記履歷類／面試類
4. 勾選「我打算做」，記錄下來並 commit
5. 履歷類建議：實際執行（改履歷），重跑缺口診斷／匹配分析，記錄落差
   位移當快速代理資料，commit——不用等面試，今天可以跑完
6. 面試前一天記錄每條建議做了沒，commit

這一波不需要介面，用 markdown 檔跑完即可。**產出的是資料，不是頁面。**

### Wave 2 — 面試後 24 小時內

7. **先不看 AI 輸出**，憑記憶寫下面試官實際問的每一題，commit
8. 打開 AI 的 8 題比對，算命中率
9. 回填「用上了嗎」「沒做的原因」
10. 對照失敗門檻，寫下這輪的判讀
11. 寫下事後訪談筆記，誠實記錄沒做的原因

### Wave 3 — 收斂日前

12. 補自己的 10 筆語料（分工承諾，目前 0 筆，用的是 Berry 整理的 7 筆）
13. 修正 `results.md` 的 ★ 題分母問題（見〈待解問題〉）
14. 改造 `alan/webapp/`：換成 Alan 的真實閉環資料
15. 發布成 Artifact

### Wave 3 的但書

介面在 Wave 3 才做，是因為它裝的是 Wave 1、2 的產出。
如果 Wave 1、2 沒跑完，介面就沒有東西可裝。

第 12、13 項優先於第 14、15 項。語料份額是對團隊的承諾，

## 第二輪：開放受試者

這輪最大的弱點是受測者、設計者、判定者同一人，N19 因此只能算自我觀察。
解法不是更嚴謹的自我判定，是換一個受試者。這一節寫清楚第二輪長什麼樣，
以及這輪的哪些技術決定是為了將來接得上。

### 第二輪要解掉什麼

| 這輪的限制 | 第二輪怎麼解 |
|---|---|
| N19 由設計者自己判 | 受試者不是設計者，事後訪談由設計者做 |
| 測不到願不願意完成填答 | 受試者第一次看到這個流程，漏斗是真的 |
| 測不到看到追問時願不願意補資訊 | 同上，N16 的入口才真的被測到 |
| n=1 | 每多一位受試者多一筆真實閉環 |

### 需要補上的東西

| 項目 | 說明 |
|---|---|
| 真的呼叫 AI | serverless function 打 Claude API，金鑰放環境變數。流程要連續，中間不能停下來等人工跑 |
| 頁面讀真實輸入 | 表單送出後直接產生結果，不是讀固定 JSON |
| 受試者招募 | 需要「即將面試、願意填完、且願意面試後回來回填」的人 |
| 資料使用同意 | 受試者不是本人，履歷與面試內容的使用範圍要先說清楚 |

### 真正的瓶頸不是技術

串 API 大概半天。找到一位符合上述三個條件的受試者，時間不確定，
而且他面試完還要願意回來填。第二輪要先解招募，不是先解技術。

### 這輪為第二輪預留的接口

| 這輪的做法 | 第二輪怎麼接上 |
|---|---|
| 頁面讀 `demo-data.json`，不把資料寫死在 HTML | 換受試者只要換一個 JSON；接 API 只要把讀 JSON 換成讀 API 回應 |
| prompt 存成獨立檔案（`prompts/`） | serverless function 直接讀同一份 prompt，兩輪跑的是同一個東西 |
| 回訪頁的欄位結構固定 | 多位受試者的資料可以直接疊起來比較 |

這些做法的成本跟寫死幾乎一樣，差別只在現在決定或之後重寫。

### 這輪實際兌現的狀態（2026-08-23 補記）

上面的接口原本是計畫，`alan/webapp/` 這輪的實作把它們兌現成了現況，記在這裡供第二輪對照：

- `demo-data.json` 已存在（`alan/webapp/demo-data.json`，在 `.gitignore` 裡，跟 `alan-data.js` 同待遇），app 改成 `fetch` 這份 JSON，不再從 `alan-data.js` 的常數載入。另有 `demo-data.example.json` commit 進 repo，結構完整、內容全遮蔽，同時是資料結構文件與換受試者的模板。
- app 這輪的角色是**純展示載體**：驗證資料（面試官實際問了什麼、建議做了沒／用上了沒）由人在 markdown 檔手動產生並 commit，時間戳由 git 提供，app 不接受即時輸入去驗證那兩件事——這是刻意的，理由見〈這一跑的定位〉。
- 面試窗口（2026-08-24 至 09-05）在寫這段時還沒發生，所以步驟 7、8（面試後回饋、缺口診斷命中）app 裡放的是**示意資料**（`demo-data.json` 的 `interviewDemo` 區塊，`isMock: true`），欄位結構跟真資料完全同構。面試後只要把 `interviewDemo` 換成真實內容、把 `isMock` 拿掉，不用改程式。
- Artifact 發布需要先過打包步驟（`alan/webapp/build.sh`）：Artifact 只能吃單檔，且 CSP 只放行 Google Fonts，原本從 jsdelivr 載的 framework7-icons 會變空白框，打包階段換成內嵌 SVG；同時遮蔽規則從「渲染時替換」搬到「寫入 dist 之前」，發布檔裡不能留原文。目前只產出 `dist/index.html`，還沒實際發布成 Artifact——公司名要不要具名尚未決定，見〈資料使用〉。

## 待解問題

### 「進階問題」改名

現有的「進階問題」（User Story ④、`c-adaptive.md`）指的是預測面試官會問什麼，
拿去跟面試官實際問題比對命中率。這個名字沒把「預測面試官提問」的本質講出來，
容易跟②追問（也是一種更深入的問題，但目的是認識自己、不驗證命中率）混淆。
待改名為「面試官提問預測」，需要同步更新的地方：`mvp-plan.md` User Story④、
`docs/glossary.md`（若也用此詞）、`alan/webapp/` 對應畫面文案。尚未執行。

### ★ 題分母不一致

`results.md` 寫「硬語料共 5 題 ★」，實際數 fixtures 檔案是 9 題：

| fixture | ★ 題數 |
|---|---|
| tech-pm-01 | 3 |
| tech-pm-02 | 3 |
| frontend-01 | 1 |
| backend-01 | 2 |
| software-engineer-01 | 0 |
| **合計** | **9** |

且 5 題不可能算出 90%（5 題只能是 0/20/40/60/80/100%）。
9 題中命中 8 題等於 88.9%，四捨五入才是 90%。

這影響發現 3（A 30% → C 90%），也就是第一輪唯一的量級差距。
三種可能：註記筆誤、當時刻意取子集、分母算錯。
逐題命中判定沒有存成檔案，目前無法從 repo 驗算。

處理方式：先反推 5 是怎麼來的，再決定要不要重算。
`results.md` 原文不改，另加一段「重判紀錄」說明。

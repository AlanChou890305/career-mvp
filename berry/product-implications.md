# 這次實驗 → 產品運用

把 MVP 驗證的成果接回產品。收斂日討論「這實驗對產品的意義」時用。
日期：2026-08-16。

前提：這是初步驗證（6 筆、單一評分者）。以下是「方向」，不是「結論」。

---

## 一、直接長成產品功能

**① 進階問題引擎 = 解法 #2「履歷經歷分析」的第一版原型**
v2 prompt 不是丟棄式實驗品，它就是「讀你的經歷 → 問出你沒交代清楚的地方」功能的雛形。
命中率（★ 經歷題 90%）證明有料，可以繼續長。

**② 「依職位型態切換追問策略」= 可寫進 spec 的產品規則**
- 經歷密集職位（PM、營運）→ 深挖式追問（v2）
- 知識密集職位（工程師硬題）→ 保留通用題廣度，別硬深挖
- 依據：v2 深挖讓 PM/後端進步，卻讓純技術題的前端退步。
- → 產品不該一招打天下，追問策略要看職位型態。

## 二、變成產品的「品質引擎」——護城河所在

**③ 命中率 SOP = N19 可驗證性的雛形**
「預測問題 → 對照真實被問 → 算命中率」這套流程，放進產品就是可驗證性功能本身：
> 使用者面試完回來勾「哪幾題真的被問到」→ 產品累積命中資料 → 越用越準。

這正是推演說的「記憶與累積」護城河：ChatGPT 給完建議就結束，
本產品會追蹤自己準不準、並越變越準。今天的 SOP 是這個閉環的手動版。

**④ 6 筆語料 = 產品長期評測集（eval set）**
prompt 每改一版、模型每換一次，都能拿這批語料回歸測試，確保沒退步。是工程資產。

## 三、確認策略方向（省下走錯的成本）

**⑤ 「護城河在經歷歸納，不在答得比 ChatGPT 好」被實測支持**
前端那筆退步 = 用數據說「別跟 ChatGPT 拼硬知識」，價值在它做不到的「記住+歸納經歷」。
→ 未來功能取捨有底氣，不會被「要不要加更多 AI 問答」帶偏。

**⑥ 背景 checklist → 該優先收哪些 profile 資料**
命中率與「背景寫得多具體」高度相關。
→ 基本資料填寫該優先收「能讓追問變尖銳」的欄位（專案、KPI、帶人經驗），而非求全。

## ⚠️ 還不能推論的（別過度延伸）

- 行動推薦（N19）還沒驗證——沒人照建議面試過，「有沒有用」仍是問號。
- 樣本 6 筆、單一評分者——趨勢可信，絕對數字別當真。
- 命中率高 ≠ 使用者願意付錢——這次測不到。

## 一句話

> 今天把「進階問題有沒有料」從假設變成「初步有料」，
> 並順手畫出產品該長的樣子（追問引擎 + 命中率閉環 + 依職位切換）；
> 但「產品會不會成功」還早，要靠補語料、驗行動推薦、收真實回饋。
